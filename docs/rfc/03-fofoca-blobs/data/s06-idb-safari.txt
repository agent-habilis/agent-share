S0.6 — IdbStore in a browser, main thread
Safari 27 (Darwin 27.0.0), localhost:8778, harness/idb/

=== why this spike exists ===

Main-thread OPFS was measured first, and disqualified. `createWritable` is
copy-on-write in Safari: the cost of a small patch tracks *file size*, not write
size.

  64 KiB random-access patch, via createWritable({keepExistingData:true})
    1 MiB file      8 ms
    8 MiB file     25 ms
   64 MiB file    117 ms          -> ~550 MiB/s, i.e. a whole-file copy

  Filling a file in 64 KiB pieces is therefore O(n^2):
    64 MiB    1024 pieces * 117 ms   = ~120 s
     1 GiB   16384 pieces * ~1.9 s   = ~8.5 h

The penalty is per createWritable() *open*, not per write. Measured separately:

  sequential write, ONE createWritable session
    1 MiB     250 MiB/s
   64 MiB     566 MiB/s            -> linear

  random 64 KiB read, file.slice().arrayBuffer(), handle reused
    1 MiB file    2.40 ms per read
   64 MiB file    2.45 ms per read  -> independent of file size
   getFile()      4 ms / 56 ms      -> scales, but once per handle

  So only random-access WRITE is quadratic. Reads were never a problem; an
  earlier reading of 217 ms was getFile() timed inside the loop.

=== IndexedDB as a block store, main thread ===

  64 MiB in 1024 x 64 KiB records, shuffled order, one transaction
    write   999 ms    64 MiB/s
    read    177 ms   362 MiB/s
  Linear in both directions; no copy-on-write cliff.

  ~24x slower than a Worker sync handle (S0.5: 955-1561 MiB/s write).
  5-50x faster than a realistic WebRTC data channel, so not the bottleneck on
  the seeding path.

=== two bugs this spike caught, neither visible to a compile check ===

1. write_verified never persisted the outboard.
   Every other backend rebuilds the outboard from the whole file on read, so
   none of them store one. The sparse path cannot: it reads only the blocks
   asked for, and has nothing to rebuild from. The nodes exist only in the
   verified stream that proved them, so decode_sparse now takes the outboard by
   &mut, carries it across calls, and IdbStore stores it alongside the range set.
   Symptom: "bound to a root whose outboard is gone".

2. Blocks were keyed by file key while range sets are keyed by root.
   Two files with identical content share a root, so completing one made the
   other advertise ranges whose blocks did not exist. Symptom: a store claiming
   a file was complete, then failing the first read with "block 1 is not held".
   Fixed by keying blocks by root too, which also deduplicates identical files.

   Note this is latent in OpfsStore for the same reason. It surfaces there as an
   error rather than as corruption, because those backends read the file at
   file.key and fail when it is short.

=== module size, for the deferred Worker split ===

  s06_idb_bg.wasm   347291 bytes   (fofoca-blobs + bao-tree + blake3, release)

  Against the 7.4 MB agent-share wasm client. A Worker carrying only the blob
  layer is a second small module, not a duplicated stack.

=== not covered ===

  Chrome. Every number here is Safari on one machine. Copy-on-write is an
  implementation choice and Chrome may not have the same cliff.
  Eviction under storage pressure. Neither OPFS nor IndexedDB was pushed to a
  quota limit, so the "advertises ranges the browser later reclaims" risk is
  reasoned about rather than measured.
