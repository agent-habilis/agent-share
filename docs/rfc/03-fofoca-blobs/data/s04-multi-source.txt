S0.4 — aggregate throughput vs source count
Captured 2026-08-03. M-series Mac, 10 cores. WebRTC transport, loopback.
Harness: mount::bench::tests::s04_multi_source_throughput_scaling (#[ignore]d).

All three runs below are of the SAME harness. Read them together: the
disagreement between them is itself a finding.

================================================================
RUN 1 — DEBUG PROFILE.  DISCARD.
================================================================
   K   aggregate MiB/s   per-source MiB/s
   1               5.2   5.2                     (1.00x baseline)
   2              22.0   10.7, 11.3              (4.24x baseline)
   4              22.5   6.0, 5.3, 5.9, 5.3      (4.34x baseline)

Unoptimized + debuginfo. Crypto and SCTP are CPU-bound in debug, so this
measures the debug build, not the transport. Superlinear K=2 is the tell.
Recorded only so the discard is on the record.

================================================================
RUN 2 — RELEASE, single pass, no repetition
================================================================
   K   aggregate MiB/s   per-source MiB/s
   1              25.3   25.3                    (1.00x baseline)
   2              10.5   5.2, 5.3                (0.42x baseline)
   4              15.8   4.1, 4.0, 3.8, 4.0      (0.62x baseline)

Contradicts run 1 in direction. A single pass through K=1,2,4 confounds the
scaling question with order and warm-up, and there is no variance estimate to
tell signal from noise. Superseded by run 3.

================================================================
RUN 3 — RELEASE, 3 reps per K, interleaved.  USE THIS ONE.
================================================================
   K       min      median         max      spread
   1      28.2        29.4        30.1      1.07x
   2      46.2        47.2        48.9      1.06x
   4      17.4        17.9        19.4      1.12x

  scaling vs K=1 (median):
    K=1: 1.00x
    K=2: 1.61x
    K=4: 0.61x

  measured median RTT: 0.3 ms
  K=1 rate 29.4 MiB/s at that RTT implies a per-connection window of ~9 KiB

Within-K spread is 1.06-1.12x, so the 1.61x effect at K=2 is well clear of the
noise floor — unlike run 2, where spread was 2.0x and the effect was not.

An earlier release run at 3 reps gave K=2 = 1.82x, spread 2.0x. Direction has
been consistent across every run performed (4.24x / 1.82x / 1.61x); only
magnitude varies.

================================================================
CAVEATS THAT MUST TRAVEL WITH THESE NUMBERS
================================================================

1. RTT is ~0.3 ms, so no flow-control window is binding — the measured rate
   implies a ~9 KiB window, not the 128 KiB RFC 01 cites. This configuration
   therefore cannot test the per-connection-ceiling claim directly. It does
   establish a floor: adding RTT makes per-connection windows bind harder and
   leaves more headroom below the shared CPU ceiling, so the multi-source
   advantage can only grow.

2. All producers and consumers share one host and one CPU. K=4 measuring worse
   than K=1 is consistent with contention at ~29 MiB/s per connection and is
   NOT explained. It should vanish at ~2 MB/s per connection, but that is a
   hypothesis, and it gates RFC 01's "cap the peer set at ~4" decision.

3. THE BENCH IS SERIAL. Per 02-performance.md finding #1 [verified],
   `fill_once` is awaited one at a time and opens its own bi-stream each time
   (mount/bench.rs:493). So K=1 is a single-stream serial number, not a
   saturated connection, and part of the K=2 gain may be pipelining rather than
   genuine multi-source capacity. The bench structurally cannot separate them.

4. The transport negotiates the data channel UNRELIABLE and UNORDERED
   (MaxRetransmits { retransmits: 0 }, fofoca-iroh-webrtc-transport
   host/jsep.rs:104-106), so the reliable-SCTP receive-window stall RFC 01
   cites as the cause is not the mechanism here.
